# 0006: Finetuning the judge (P5)

Date: 2026-09-26. Status: **accepted**, for synthetic data. The finetuned Q4_K_M judge meets the
adoption rule on all three eval sets (*Results*). Realistic text (P7) is still the open check.

## Context
After 0005 the zero-shot judge (Qwen3-1.7B Q4_K_M, prompt v2) meets the gated numbers on the
synthetic test split. Two weaknesses are left for a finetune:
- **Lab and bill values after a bare lab word.** On the hard set, `PLT`, `platelets` and
  `total bill` values are never dropped; 5 of 60 were accepted as a phone, MRN or case number.
- **Category confusions.** `category_uncertain` is most of the gold review load. On test the
  model-judged confusions are mostly ID against ID: phone → email (3), case ↔ MRN (3),
  NRIC ↔ MRN (3), device → an ID (3), plus 3 misplaced DOBs read as `none`.

## Decision

### What is trained
Only the **Choice question**, the one production asks. Each example is the exact prompt the judge
sends (system prompt, prefix, stem, lettered options, `Answer with one letter:`); the target is the
gold option's letter. `judge.question` builds both, and a test checks that every training prompt
is byte-identical to one the judge sends. The prompt is unchanged, so `PROMPT_VERSION` stays 2.

- **Loss on one token.** The judge reads probabilities from the first answer token, so the loss is
  cross-entropy at that position only. Batches are left-padded and the model computes logits for
  the last position alone.
- **Rotations.** Each candidate is asked under 2 random cyclic rotations of its options, so the
  model learns the option, not the letter.
- **Fast-path spans are left out**: the model never sees them in production.

### Data (`finetune/build_data.py`, `slmjev.sft`)
| Source | Split, seed | Docs |
|---|---|---|
| Main corpus (`synth.generate`) | train, 1000 | 600 notes + 900 cells |
| Hard decoys (`synth.generate_hard`) | train, 1001 | 300 |
| Lab/bill decoys (`synth.generate_labs`, new) | train, 1002 | 600 |
| Validation (the same three) | dev, 1010-1012 | 190 |

- 14,276 training examples from 7,138 candidates (3,798 gold, 3,340 decoys); 1,128 validation
  examples.
- `generate_labs` writes short notes where lab and bill values are shaped like postal codes,
  phones and MRNs, next to gold identifiers of the same shapes, some without a keyword. The model
  cannot learn "6 digits after a word means `none`".
- **Held out.** The calibration set (train seed 21) and every eval set (test 31, 41, 51; dev 11) are
  regenerated by the builder, and any identical document text is dropped (139 short cells). The
  test split also uses unseen name, street and building pools. `generate_labs` gives test its own
  **unseen lab and bill lead words** (`thrombocytes`, `RBC`, `amount payable`, …), so the eval
  measures whether the fix generalises beyond the words it was trained on.

### Training (`finetune/train_judge.py`)
- **LoRA on bf16 weights, not QLoRA.** At 1.7B the bf16 model (about 3.4 GB) fits the 8 GB
  RTX 4060 with gradient checkpointing. Merging a LoRA trained on 4-bit weights into bf16 weights
  adds a mismatch; this avoids it. The only quantization is the final Q4_K_M, which the eval
  measures. QLoRA stays the option for a larger tier.
- **Hyperparameters.** r = 16, alpha = 32, dropout 0.05, on all attention and MLP projections;
  lr 1e-4, cosine with 3% warmup; batch 8 × accumulation 2; 1 epoch. These follow the finetune_slm
  plan, except that the effective batch is 16 examples rather than 16 accumulated single ones.
- **Checkpoint choice.** Validation loss and per-label accuracy are logged every 100 steps. The
  adapter with the best validation loss is kept; if nothing beats the base model, no adapter is
  written.
- **Runtime.** It runs offline in the Unsloth Studio venv, which already has torch 2.11 + CUDA 12.6,
  transformers and peft, so nothing new is installed. The hub is forced offline, `netguard` closes
  non-loopback sockets, and the base model loads with `local_files_only`.

### Export (`finetune/export_gguf.py`)
Merge the adapter, convert with the local llama.cpp's `convert_hf_to_gguf.py` to a bf16 GGUF, and
quantize with `llama-quantize` to **Q4_K_M**, the zero-shot tier, so memory and latency stay
comparable. SHA-256 sums go to `models/p5/export.json`. All of `models/` is gitignored.

### Base weights: the one download
Training needs Hugging Face weights; only the Q4_K_M GGUF is on disk. The proposal is
`Qwen/Qwen3-1.7B` (bf16 safetensors, about 4 GB), the base the current GGUF was quantized from.
It goes to `models/base/Qwen3-1.7B` and is gitignored. The user approved it on 2026-09-26, and it
was fetched anonymously (no saved token). Nothing else was downloaded.

### Evaluation, once trained
Same harness and configuration as 0005 (`--prod`), with the new GGUF:
1. **Train seed 21**, then refit calibration. The fit refuses the v2 file automatically, because
   the model basename changed.
2. **Test seed 31**, calibrated: the gated numbers, against 0005's v2 column.
3. **Hard seed 41**: lab words seen in training, but a template the training never used.
4. **Labs, test seed 51**: unseen lab words.
5. The same four runs for the zero-shot model on the labs set, so there is a baseline to compare.

The finetune is adopted only if direct-identifier recall does not drop (the release gate) and
auto-accept precision and review rate do not get worse on test. Rows go to `eval-log.md`.

## Results
**Training.** 893 steps (1 epoch) in 67 minutes; peak VRAM 4.45 GiB. Validation loss fell from
2.679 (base) to 0.0195 at the last step, which was kept; validation accuracy was 0.993. The merged
model was exported to Q4_K_M (1.11 GB, the same tier as zero-shot). Six validation prompts render
identically under llama-server and the HF chat template.

**Eval.** All runs are `--prod` on CPU, with calibration refit on train seed 21. The zero-shot
column is 0005's v2 model and calibration. On the labs set, the zero-shot column also uses v2
calibration.

- **Adoption rule: met.** Direct recall did not drop anywhere. Auto-accept precision and review
  rate improved or held on every set.
- **Unseen lab words.** The labs test set uses lead words that training never saw (`thrombocytes`,
  `RBC`, `amount payable`, …). All 395 decoys were dropped, against 209 zero-shot. The fix
  generalises beyond the trained words, at least within the generator's clause templates.
- **Category confusions.** Test review fell from 27 items to 8: 6 gold `category_uncertain`, 1
  `column_outlier` and 1 `uncertain`, with no decoys. The ID-vs-ID confusions from 0005 are gone.
- **Latency.** Unchanged or better, because the tier and the call count are unchanged.

### Calibration: a fail-closed cap on `drop_below`
The first refit was **fail-open**, so it was rejected. The finetuned scores are separable on train
seed 21, so identity calibration won the CV comparison. The recall rule then put `drop_below` at
its old 0.5 cap, because every training positive scored above 0.98. With that cut, the train
replay dropped a misplaced DOB at p = 0.16, and the test replay dropped one at p = 0.30. Neither
went to review.

`calibrate.MAX_DROP` = 0.05 now caps `drop_below`: no span with more than a 5 % calibrated chance
of being an identifier is dropped unreviewed. The cap is `--max-drop` in `fit_calibration.py` and
is recorded in the calibration meta; a note is added when it applies. The zero-shot fits
(0.0246, 0.0217) were already under it, so they are unchanged. The P5 fit is now: identity,
`drop_below` 0.05, `accept_at` 0.967. Both DOBs go to review, and a test pins the case.

## Risks
- **Synthetic overfit.** Training and test share the generator's templates, so test gains
  overstate real gains. The unseen pools and lab words limit this but do not remove it; P7's
  realistic text is the real check.
- **Saturated confidence (observed).** On the hard and labs sets the model scores are essentially
  0 or 1: ECE 0.000, and nothing falls in the review band. On synthetic data every call was right.
  On real text, though, an error will likely be **confident**, so it is dropped or accepted without
  review instead of flagged. The `MAX_DROP` cap limits the drop side only above 5 %. P7 must
  measure this on realistic text before the finetune is used on real data. If errors show up
  there, the options are label smoothing, a temperature floor, or keeping the zero-shot model as a
  second opinion.
- **Letter tokens.** Letters must be single tokens, and they must be the first answer token after
  the chat template. The trainer checks both. After export, the llama-server rendering of one
  prompt should be compared with the HF template before any eval.
